# qc_step3 — 유니버스 + 팩터 점수 + 종목 구성·매매 참고 노트

1세대 프로그램 매매 모델(plan_v4.3.md) 3단계. 1단계 월말 유니버스와 2단계 팩터 z로 계획서 6장 '구성'(밴드 규칙·동일가중/역변동성·5% 상한)에 따라 보유 종목을 정하고, 9장 체결 시간 규칙에 따라 다음 거래일 MOC로 매매한다.
- 평가(매매)는 2003-01 신호일부터다(사용자 결정, 아래 "기록").
- 비용은 IB 수수료만 넣는다(스프레드·슬리피지·저/기본/고 시나리오는 4단계). 3단계 수익률은 스프레드가 빠져 성과 판단에 쓰지 않는다.
- `qc_step1/`·`qc_step2/`는 백업으로 그대로 둔다.

코드 주석의 `NOTES.md [X] 참고`는 아래 "확인 필요" 목록의 해당 항목을 가리킨다. 2단계 정의는 "2단계 팩터 정의", 3단계 정의는 "3단계 구성·매매 정의" 절에 있다.

## 파일 구성

| 파일 | 내용 |
| --- | --- |
| `main.py` | `QCAlgorithm` 클래스: `initialize`(파라미터·브로커·시드·예약 이벤트), 월별 흐름(유니버스 → 재무 스냅샷 → 팩터 → 리밸런싱 계획), 체결일 MOC 제출, 체결·상장폐지 이벤트 |
| `config.py` | 모든 설정 상수와 채택 결정 주석(계획서 절 번호 포함), `QUICK_TEST` |
| `universe.py` | 적격 조건, 대표 주식 선정, 완충 순위, 탈락 사유 분류, 시점 규칙(공시 다음 거래일·거래소 달력), 날짜 보조 함수 |

| `portfolio.py` | 파라미터 검증, σ̂(EWMA), 밴드 규칙 선택, 목표 비중(동일가중·역변동성·5% 상한), 신호일 종가 기준 정수 주 주문 계획, 체결·보유 통계 누적(`TradeBook`), 첫 매매 이후 성과 계산(`performance`) |

| `report.py` | 3단계 로그: `[CONFIG]` 3단계 줄, `[REBAL]`, `[FILL]`, `[PYEAR]`, `[PERF]`, `[SUMMARY]` 끝의 portfolio 요약과 3단계 런타임 통계(출력은 diagnostics의 key_log·summary로) |
| `coverage.py` | 데이터 커버리지 점검 모드(`COVERAGE_CHECK`)의 `[COV]` 진단. 1단계 함수만 쓴다 |

의존 방향: `main` → `report`·`coverage` → `diagnostics`(main이 만든 Recorder를 받아 씀) → `portfolio` → `factors` → `universe` → `config`. `main`은 아래 모듈을 직접 부르기도 한다. 거꾸로 가는 import와 순환 import는 없다.

## QuantConnect에 올리는 법

1. 웹 IDE에서 새 프로젝트를 만들고 `main.py`를 이 폴더의 `main.py` 내용으로 바꾼다.
2. 같은 프로젝트 최상위에 `config.py`, `universe.py`, `factors.py`, `portfolio.py`, `diagnostics.py`, `report.py`, `coverage.py` 파일을 만들어 각각 붙여 넣는다(하위 폴더 없이, .py 8개). `coverage.py`는 점검 모드를 쓰지 않아도 main이 import하므로 올려야 한다.
3. 프로젝트 파라미터(Project → Parameters)에 `n_holdings`(40·60·80)와 `weighting`(equal·invvol)을 넣는다. 없으면 60·equal이다. 시험 집합 밖 값이면 initialize에서 오류로 멈춘다.
4. `config.QUICK_TEST = True`(기본)면 2001-01-01~2004-12-31만 돈다(2001~2002는 준비 구간, 2003-01 첫 매매). 최종 확인 때만 False(1998-01-01~2015-12-31)로 바꾼다.
5. `NOTES.md`는 로컬 참고용이라 올리지 않아도 된다.

### 모듈 import 방식 (확인 상태)

- 같은 프로젝트의 `.py` 파일은 `from 모듈이름 import 이름` 형태로 가져온다는 것이 QuantConnect 포럼 안내와 일치한다([포럼 6022](https://www.quantconnect.com/forum/discussion/6022/import-user-created-python-modules-additional-files-to-organize-code-into-main-py-in-web-editor/), [포럼 13665](https://www.quantconnect.com/forum/discussion/13665/how-to-import-classes-from-other-python-files/)). 알고리즘 클래스는 `main.py`에 직접 정의해야 하고, 다른 파일이 `main.py`를 import하면 순환 import가 된다.
- `from config import *`는 표준 파이썬 문법이라 같은 방식으로 동작할 것으로 보지만, 공식 문서에서 와일드카드 예시를 직접 확인하지는 못했다. **확인 필요.** 첫 실행에서 `NameError`나 `ImportError`가 나면 알려 줄 것.
- **확인 필요:** 모듈 이름 `config`·`universe`·`diagnostics`가 QuantConnect 환경에 설치된 다른 파이썬 패키지와 겹치면 엉뚱한 모듈이 불릴 수 있다. 첫 실행 때 `[CONFIG]` 로그가 정상 출력되면 `config`는 이 프로젝트 파일이 불린 것이다. 문제가 생기면 `step1_config.py`처럼 이름을 바꾼다.
- LEAN 형식(`Resolution`, `Universe`, `DataNormalizationMode`, `QCAlgorithm`)을 쓰는 파일은 각자 `from AlgorithmImports import *`를 둔다(`main.py`, `universe.py`, `factors.py`, `diagnostics.py`). `config.py`는 LEAN 형식을 쓰지 않는다.
- 모듈 이름 `factors`도 위와 같은 이름 겹침 확인 대상이다.

## 출력

- **콘솔 로그(3단계):**
  - `[CONFIG]` 4줄. 넷째 줄이 3단계 설정이다: n·weighting·quick_test·실행 구간(period)·평가 시작(`portfolio_start=2003-01`과 이유)·밴드·상한·σ̂·최소 거래·현금 버퍼·MOC 시각·브로커·`costs=fee_only`·구독 방식.
  - `[START]`, `[FACTOR]`(점수가 처음 나온 두 신호일), `[SPOT]`, `[SUMMARY]`.
  - `[REBAL]`(처음 두 번 리밸런싱): 신호일·체결 예정일, 유지·매도(사유별)·신규 수, 빈자리(`empty`), σ̂ 부족으로 뺀 수(`novol`), 주문 수, 생략 수(금액), 못 산 금액(`unbought`), 목표 대비 비중 오차 최대(`werr_max`), 계획상 현금 비중, 5% 상한 도달 수, 매수 축소 여부, 신호일 포트폴리오 가치.
    - 첫 줄 끝의 `uni=…`·`zt=…`는 그 신호일(2003-01) 유니버스와 z의 CRC32 지문이다. 빠른 실행(2001 시작)과 전체 실행(1998 시작)의 첫 포트폴리오 입력이 같은지 QC에서 이 값으로 비교한다.
  - `[PERF]`(종료 시, debug): 첫 매매 이후 성과. QC 결과 화면 통계에는 1998년부터의 현금 구간이 섞이므로 따로 계산한다. `costs=fee_only`(스프레드 미포함, 성과 판단용 아님).
    - `base`: 첫 체결 전날 종가(전액 현금, 출발 가치). `first_fill`: 첫 체결일. `end`: 마지막 종가일. `yrs`: 달력일/365.25.
    - `cagr`, `vol`(일간 수익률 표본표준편차 × √252), `sharpe`(무위험 0, 평균/표준편차 × √252).
    - `mdd`: 일별 가치의 직전 고점 대비 최대 하락이다. 괄호 안은 고점일>저점일과 회복일(고점 가치를 다시 넘은 첫날, 없으면 none).
    - `SPY`: 같은 날짜들의 SPY 조정가(배당 포함 총수익 대용) CAGR·MDD.
    - 가치는 매 거래일 개장 뒤 점검 때 전날 종가로 평가한 값이다.
  - `[FILL]`(처음 두 번 리밸런싱, 리밸런싱당 표본 5건): 체결 다음 날 체결일 원주가 일봉 종가를 받아 체결가와 비교(`ok`여야 함), 주문 제출 시각, 체결 시각, 수수료. 주문이 없던 리밸런싱은 표본이 없다.
  - `[PYEAR 연도]`: `hold`(일평균 보유 수), `to`(연간 편도 회전율 = Σ체결 금액/체결 시점 가치 ÷ 2), `orders`, `fee`(달러, 연평균 자산 대비 %), `skip`(생략 거래 수), `empty`(채우지 못한 자리 합계), `cash`(일평균 현금 비중), `cap`(5% 상한 도달 수), `delist`(보유 종목 상장폐지 이벤트), `rej`(취소·무효 주문), `neg`(현금 음수 발생일), 역변동성이면 `novol`.
  - `[SUMMARY]` = 1단계 요약 + `| factors:` + `| portfolio:`(연평균 편도 회전율·수수료 %, 생략 거래, 현금 음수일, 무효 주문, 늦은 실행, 평균 보유 수·현금 비중, 최대 노출). 첫 매매 이후 성과는 `[PERF]`에 있다.
  - 로그 한도(백테스트당 10KB) 때문에 끄는 줄: `[YEAR]`·`[UNIV]`(`LOG_STEP1_YEAR = False`), `[FYEAR]`(`LOG_STEP2_YEAR = False`), `[LEGEND]`·`[DIAG]`(`LOG_STEP1_CHECKS = False`). 계산은 그대로다.
  - **핵심 줄(`Recorder.key_log`):** `[CONFIG]`·`[START]`·`[SUMMARY]`·`[WARN]`·`[PERF]`는 `debug`로만 남긴다. 2단계 실제 로그에서 debug 줄도 로그 파일에 기록되어 log와 함께 쓰면 두 번 찍혔다. 나머지 줄은 `log`만 쓴다.
  - **런타임 통계(종료 시 1회):**
    - 1·2단계 7개: `months`·`first_sig`·`n_avg`·`gone`·`cov_avg`·`cov_min99`·`q4`.
    - 3단계: `turnover`(연평균 편도 회전율)·`fee_pct`(연평균 수수료 %)·`avg_hold`·`cash_avg`(%).
    - `[PERF]`: `p_cagr`·`p_vol`·`p_mdd`(%), `p_sharpe`, `spy_cagr`·`spy_mdd`(%).
  - **크기(가짜 QC 시험, N=60 equal):** QUICK_TEST(2001~2004)는 log 1,518 + debug 1,935 = 3,453바이트, 전체 기간(1998~2015)은 log 3,867 + debug 1,940 = 5,807바이트였다. 실제 데이터는 숫자가 길어 조금 더 크다. `[WARN]`은 한 줄에 최대 약 210바이트씩 더해진다.
  - `[SPOT]` 형식: `mom=12-1 수익률(%) q=gp/ta,ni/ta,tl/ta v=e/p,b/p,fcf/p,s/p $B=시총,TTM 매출,TTM 순이익,총자산(십억 달러) fd=사용한 공시일 ttm=q4|ttm12 z=…`(제외면 `excluded=사유`). 비율은 배수다(0.038 = 3.8%).
- **Object Store:** 월별 전체 기록 CSV, 종목별 진입·탈락 기록 CSV. 무료 플랜에서 권한 오류가 나서 기본으로 저장하지 않는다(`config.SAVE_TO_OBJECT_STORE = False`, [H]). 켠 경우에만 아래 방법으로 읽는다.
- **차트:** Universe(유니버스·적격 종목 수), Universe Flow(진입·탈락 수), 벤치마크 SPY(QC 기본 차트). RSP 비교는 나중 단계.

## 확인 필요 (QuantConnect API) — 확정하지 않은 부분과 확인 방법

- **[A]** 선택 함수가 받는 Fundamental 가격·시총이 '직전 거래일 종가' 기준인지.
  → `[START]`의 `price_match`(표본의 Fundamental 가격 = 신호일 원주가 종가인 수)가 표본 수와 같으면 확인됨. 선택 함수 호출 시점과 신호일 규칙은 [F] 참고.
- **[B]** `Fundamental.price`가 비조정 원주가인지. → [A]와 같은 값. `price_match`가 낮으면 조정가일 가능성.
- **[C]** Morningstar 필드 값: `security_type` 코드, `exchange_id`, `country_id`, `company_id`, `is_depositary_receipt`, `is_reit`, `ipo_date`, `morningstar_sector_code`. 2026-09-23 피드 교체 뒤에도 LEAN 속성 이름은 유지된다고 공지됐지만 값의 정의는 바뀌었을 수 있음. → `[DIAG]` 값 분포, CSV의 `drop_*` 열.
- **[D]** `financial_statements.file_date`의 존재·형식. → `[DIAG]` `file_date_type`, `[START]` `filing`, CSV `file_date_missing` 열.
- **[E]** 시총의 발행주식수가 '공시 다음 거래일' 규칙을 지키는지. 이 단계에서 재무 자료가 섞이는 곳은 순위에 쓰는 Morningstar 시총의 발행주식수뿐이다. 시총 내부의 주식수 갱신 시점은 코드로 되돌릴 수 없으므로, 유니버스 종목마다 최신 재무 공시일이 신호일 기준으로 아직 쓸 수 없는 경우(`universe.filing_usable`이 False)를 `pit_late`로 세어 기록한다. 2단계 팩터는 원 항목을 쓰고, `factors.financial_state`가 같은 `filing_usable`로 사용 여부를 강제한다(아래 "2단계 팩터 정의"). → CSV `pit_late` 열.
- **[F]** `SecurityExchangeHours.get_previous_trading_day` / `get_next_trading_day`. → 실패하면 `[WARN]` 로그. 2002-03·2013-03 신호일이 성금요일 전날(2002-03-28, 2013-03-28)이어야 한다.
  - **선택 함수 호출 시점(2026-09-26 실행 관측):** 예전에는 '`self.time`의 달이 바뀐 첫 호출'에서 재구성했다. 그러자 월말이 금요일인 달의 신호일이 다음 달 첫 거래일로 잡혔다(`sig=1998-02-02`, `1998-03-02`, 연도별 `months`가 11·13으로 흔들림). 선택 함수가 데이터 날짜의 다음 날(주말 포함)에 불리는 것으로 보인다. 금요일 데이터는 토요일(아직 이전 달)에 들어오고, 새 달의 첫 호출은 월요일 데이터를 가진 화요일 호출이 된다(관측에서 한 추정).
  - **신호일 규칙(계획서 9장: 신호는 월말 마지막 거래일 종가):** 매 호출에서 `data_date` = `self.time` 기준 직전 거래일을 구한다. `data_date`의 다음 거래일이 다른 달일 때(= `data_date`가 그 달 마지막 거래일)만 재구성하고 `signal_date = data_date`로 둔다. 같은 `signal_date`로는 두 번 재구성하지 않는다(`main._last_signal_date`). 첫 신호일 확인(`[START]`)도 이 신호일에서 한다. 1997-12-31을 데이터 날짜로 한 호출이 있으면 그 호출에서 확인이 먼저 이뤄진다.
  - **기대:** 첫 `sig=1998-01-30`, 이후 모든 신호일이 각 달 마지막 거래일, 연도별 `months=12`(2015는 11), 총 215개월. Object Store를 끈 상태에서는 `[YEAR]`의 `months`와 `[SUMMARY]`의 `months`·`first_sig`·`last_sig`로 확인한다.
  - **빈 데이터:** 월말 호출의 데이터가 비어 있으면 재구성하지 않고 전달 구성 종목을 그대로 유지한다. `[WARN] empty month-end data sig=YYYY-MM-DD, previous universe kept`를 신호일마다 한 번 남긴다. 그 신호일은 처리하지 않은 것으로 되돌리므로 같은 데이터 날짜로 다시 불리면 재구성을 재시도한다. 다시 불리지 않으면 그 달은 전달 구성으로 넘어간다. 데이터 시작일(`LEAN_DATA_START`, 1998-01-02) 전 날짜의 빈 호출은 경고 없이 넘어간다. 두 경우 모두 `[SUMMARY]`의 `empty_calls`에 센다.
- **[G]** `symbol.id.date`가 최초 거래일이고, 데이터 시작 전 상장 종목은 `LEAN_DATA_START`(1998-01-02)인지. → `[DIAG]` `ipo_missing` `presample_pass`·`sid_pass` 수.
- **[H]** 무료 플랜 로그 한도(백테스트당 10KB로 안내됨)와 Object Store 사용 가능 여부. → 로그 잘림, `[WARN] object store` 로그. Object Store는 무료 플랜에서 권한 오류가 나서(2026-09-26 실행) 저장을 끈다(`config.SAVE_TO_OBJECT_STORE = False`). 로그 출력은 그대로다.
  - **debug 제한(QuantConnect Logging 문서 안내):** 메시지 하나가 200자까지다. 1초 안에 여러 개를 보내면 속도 제한이 걸린다. 로그 한도에 포함되지만 한도를 넘어도 콘솔에는 나온다. 같은 내용을 여러 번 남기면 로그 파일에는 처음 것만 들어간다([Logging 문서](https://www.quantconnect.com/docs/v2/writing-algorithms/logging)).
  - 2단계 실제 실행에서 debug 줄이 로그 파일에도 기록되어 핵심 줄이 두 번 찍혔다. 그래서 3단계 `key_log`는 debug만 쓴다.
  - **확인 필요:** 200자가 넘는 핵심 줄(`[CONFIG]` 4줄 약 200~330자, `[SUMMARY]` 약 450~550자)이 로그 파일에 잘리지 않고 남는지, 한꺼번에 나가는 `[CONFIG]` 4줄이 1초 속도 제한으로 빠지지 않는지.
  - **확인 필요:** `set_runtime_statistic`으로 넣은 값이 백테스트 결과 화면의 런타임 통계에 보이는지.
- **[I]** `history(..., data_normalization_mode=DataNormalizationMode.RAW)`와 결과 DataFrame 색인(symbol, time) 형식. → 실패하면 `[WARN] history` 로그. `[DIAG]` share_class 줄의 adv 값이 0이 아니고 CSV `adv_missing`이 작으면 정상. 2단계 모멘텀은 같은 방식의 범위 요청(`history(symbols, start, end, Resolution.DAILY, data_normalization_mode=DataNormalizationMode.ADJUSTED)`)을 쓴다. 실패하면 `[WARN] adjusted history request failed`가 나오고 모든 종목이 `mom` 제외가 된다.
- **[J] (2단계) Morningstar 재무 필드 이름·의미.** 쓰는 경로는 `config.FLOW_FIELDS`·`BALANCE_FIELDS`·`PERIOD_END_FIELD`(모두 `financial_statements` 아래)이고, 공식 문서에서 이름을 직접 확인하지 못했다. 이름이 틀리면 알고리즘을 멈추지 않고 `[WARN] field missing: financial_statements.…`를 한 번 남긴 뒤 그 값을 결측으로 처리한다.
  - **분기값과 연간값:** QuantConnect 포럼에 따르면 `twelve_months`는 최근 12개월 합(TTM)이 아니라 회계연도 연간 값이다([포럼 11002](https://www.quantconnect.com/forum/discussion/11002/trailing-12-month-financials/), [포럼 4869](https://www.quantconnect.com/forum/discussion/4869/requesting-trailing-12-month-fundamentals/)). 그래서 TTM은 `three_months`(분기) 4개 합을 원칙으로 하고, 그렇게 만들 수 없을 때만 `twelve_months`(연간)를 쓴다. 2026-09-23 피드 교체 뒤에도 같은지, 분기값이 믿을 만하게 채워지는지는 첫 실행의 `[FACTOR]` `ttm:q4/ttm12/none`과 `[FYEAR]` `q4=`(분기 합 비율)로 판단한다.
  - **결측 표현:** 결측이 NaN으로 오는지 0으로 오는지 확인하지 못했다. NaN만 결측으로 본다. `[FACTOR]` `chk:rev_zero`(TTM 매출이 0인 종목 수)가 크면 결측이 0으로 오는 것이다.
  - **부호:** `chk:capex_pos`는 설비투자가 양수로 온 종목 수다. FCF는 부호와 무관하게 `영업현금흐름 − |설비투자|`로 계산한다(계획서 8장 부호 규칙).
  - `chk:assets_single`은 1년 전 공시가 없어 최신 총자산만으로 평균 총자산을 계산한 종목 수다.
- **[K] (2단계) 모멘텀 시작 시점.** 12-1개월 모멘텀에는 t-12개월 월말 종가가 필요하다. QC 가격 데이터가 1998-01-02부터라면 1998년 신호일(1998-01~1998-12)은 모든 종목이 `mom` 제외가 되어 점수 산출이 0이고, 첫 점수는 1999-01 신호일에 나온다(1998-01 월말 종가를 시작점으로 사용). 규칙(최소 12개월 관측)대로의 결과다. 그래서 `[FACTOR]` 상세는 점수가 처음 나온 두 신호일(1999-01, 1999-02 예상)에 남긴다(아래 "기록").

## 2단계 팩터 정의 (계획서 6장 표 기준)

- **계산 대상:** 매월 신호일(1단계와 같은 월말 마지막 거래일)의 유니버스 종목 전체.
- **재무 시점:** 매월 신호일에 적격 종목 전체의 재무 스냅샷(공시일, 기간 종료일, 원 항목의 분기·연간 값, 총자산·총부채·순자산)을 Symbol별로 저장한다. 신호일에는 공시 다음 거래일 규칙(`universe.filing_usable`, 1998~2012 근사 구간 추가 시차 포함, 현재 0)을 통과한 스냅샷 중 공시일이 가장 늦은 것을 쓴다. 이번 달 스냅샷의 공시가 아직 사용 불가면 예전 스냅샷이 쓰인다.
  - 만료: 그 공시일로부터 180일이 지나면(`신호일 − 공시일 > 180일`) 재무를 결측으로 처리한다(사유 `expired`).
  - 스냅샷은 있는데 사용 가능한 것이 하나도 없으면 사유 `pit`다.
  - **한계:** 월말에만 스냅샷을 찍으므로, 두 월말 사이에 나왔다가 다음 월말 전에 대체된 공시(예: 같은 달 정정 공시)는 놓칠 수 있다. 백테스트 초기(1998년)에는 이력이 짧아 분기 합 대신 연간 값, 평균 총자산 대신 최신 값이 쓰인다. 유니버스 진입 전 이력도 쓰도록 유니버스가 아닌 적격 종목 전체를 저장한다.
- **TTM:** 최신 사용 가능 공시부터 기간 종료일이 연속인 4개 분기(간격 75~105일)의 `three_months` 합(`q4`)이다. 흐름 항목 5개(매출·매출총이익·순이익·영업현금흐름·설비투자)가 네 분기 모두 있어야 한다. 아니면 그 종목·월은 최신 공시의 `twelve_months`(연간 값, `ttm12`)를 쓰고, 그것도 없으면 `none`이다. 방식은 종목·월마다 하나로 정하고 매월 센다.
- **평균 총자산:** (최신 사용 가능 공시의 총자산 + 1년 전 공시의 총자산) / 2. 1년 전 공시는 최신 공시 기간 종료일에서 365일 전에 가장 가까운 과거 공시다(동률이면 나중 공시). 과거 공시가 하나도 없으면 최신 총자산만 쓴다.
- **지표와 해석(확인 요청):**
  - 모멘텀: 배당·분할 조정 가격(`DataNormalizationMode.ADJUSTED`)으로 t-12개월 월말 종가 → t-1개월 월말 종가 수익률. 유니버스 종목 전체를 한 번의 history 요청으로 받는다. '최소 12개월 관측'은 t-12..t-1 열두 달 모두에 월말 종가가 있는 것으로 해석했다.
  - 퀄리티: TTM 매출총이익 / 평균 총자산, TTM 순이익 / 평균 총자산, 총부채 / 총자산(최신 공시, 낮을수록 좋음). **총부채는 부채총계(`total_liabilities_net_minority_interest`)로 해석했다(차입금 합계가 아님).**
  - 가치: TTM 순이익 / 시총, 순자산(보통주 자본 `common_stock_equity`) / 시총, TTM FCF / 시총, TTM 매출 / 시총. 시총은 1단계와 같은 신호일 Morningstar 시총이다. 음수 순이익·FCF는 그대로 낮은 값, 순자산 ≤ 0은 순자산/시총 결측이다. 매출총이익은 손익계산서의 `gross_profit` 항목을 쓰고, 순이익은 `net_income`이다.
- **결측·제외(계획서 6장 재무 결측):** 모멘텀 필수, 퀄리티 3개 모두 필요, 가치 4개 중 3개 이상 필요(1개 결측은 0점, 항상 4로 나눔). 미달이면 그 달 점수 대상에서 뺀다.
  - 사유는 `mom`, `expired`, `pit`, `qual`, `value`이고 한 종목이 여러 사유를 가질 수 있다.
  - 재무가 `expired`·`pit`이면 `qual`·`value`는 따로 세지 않는다. 재무 자료가 전혀 없으면 `qual`·`value`로 센다.
- **점수:** 섹터(합친 그룹) 안에서 지표별 순위를 평균 순위(동점)로 [-1, 1]에 옮긴다(`2(r−1)/(n−1) − 1`, 1개면 0). 총부채/총자산은 부호를 바꿔 순위를 매긴다.
  - 스타일 점수: 모멘텀은 그 순위 점수, 퀄리티는 3개 평균, 가치는 합/4.
  - 복합 점수 = 세 스타일 평균. z = 복합 점수를 그 달 점수 대상 전체에서 평균 0·표준편차 1(모표준편차, ddof=0)로 다시 표준화한 값.
  - 최근 달의 z는 `main._factor_z`에 둔다(다음 단계 입력). 전역 순위 점수(비교 실험)는 만들지 않았다.
- **섹터 합침('인접'의 정의, `config.SECTOR_MERGE_ORDER`):** Morningstar 섹터 코드 순서 101 → 102 → 205 → 206 → 207 → 308 → 309 → 310 → 311(금융 103·부동산 104는 유니버스에서 제외)에서 바로 앞·뒤 그룹을 인접으로 본다.
  - 점수 대상이 20개 미만인 그룹 중 가장 작은 것부터, 앞·뒤 중 종목이 적은 쪽(같으면 뒤)과 합친다. 모든 그룹이 20개 이상이 되거나 한 그룹이 될 때까지 반복한다.
  - 이 순서는 Morningstar 상위 분류(경기민감 101·102 / 방어 205~207 / 민감 308~311)를 이어 붙인 것이라, 경계(102↔205, 207↔308)에서는 상위 분류가 다른 섹터끼리 합쳐질 수 있다.
  - 합친 조합은 `[FACTOR]` `merge=`(예: `Util+Comm(12+30)`)에, 합친 달 수는 `[FYEAR]` `merge_m=`에 남긴다.

## 3단계 구성·매매 정의 (계획서 6장 '구성'·'변동성 σ̂'·'소액 거래', 9장 체결 시간 규칙, 4장 제약)

- **사용자 결정(결과 보기 전 동결):** N ∈ {40, 60, 80}, 가중 ∈ {equal, invvol}. QC 프로젝트 파라미터 `n_holdings`·`weighting`(기본 60·equal)이고 `[CONFIG]`에 찍힌다. 정수 주만 산다. 비용은 IB 수수료만이다.
- **신호와 첫 구성:** 매월 신호일(월말 마지막 거래일)의 2단계 z를 쓴다. 평가 시작 신호일(`PORTFOLIO_START_SIGNAL = (2003, 1)`, 사용자 결정) 전에는 유니버스·z만 계산하고 주문하지 않는다(현금). 첫 포트폴리오는 2003-01 신호일(2003-01-31)의 z 상위 N이고, 체결은 2003-02-03 MOC다.
- **이후 매월(밴드 규칙):** 보유 종목은 (a) 그 달 점수 대상 중 z 순위 ≤ 0.4 × 점수 대상 수이고 (b) 1단계 유니버스(상위 1,100 버퍼) 구성 종목이면 유지한다. 아니면 매도한다.
  - 매도 사유: `universe`(유니버스 이탈), 점수 결측 사유(`mom`·`qual`·`value`·`expired`·`pit` 중 첫 번째), `band`(상위 40% 밖), `no_vol`(역변동성에서 σ̂ 부족).
  - 빈자리는 z 순위 ≤ 0.2 × 점수 대상 수인 종목 중 보유하지 않은 것을 점수순으로 채운다. 다 못 채우면 남은 자리는 현금이고 `empty`로 센다.
  - z 동점은 SID 문자열 순이다.
- **목표 비중:** 자리당 1/N. 보유 종목 비중의 합 = 보유 수/N이고, 빈자리 몫은 현금이다.
  - equal: 보유 종목마다 1/N.
  - invvol: 보유 몫 합을 1/σ̂에 비례해 나눈다. σ̂ = 조정 종가 일간 단순 수익률 최근 252개의 EWMA 표준편차(반감기 60거래일, 평균 0 가정, 최소 126개). σ̂가 없는 종목은 역변동성안에서 뺀다(신규 후보는 건너뛰고, 보유 종목은 `no_vol`로 매도). `novol`로 센다.
  - 5% 상한: 넘는 종목을 5%로 자르고 초과분을 나머지에 비중 비례로 재분배하며, 넘는 종목이 없을 때까지 반복한다. `cap`으로 센다.
- **수량(계획서 9장):** 신호일 다음 날 0시 선택 함수에서, 신호일 종가(Morningstar 원주가)와 그 시점 포트폴리오 가치(신호일 종가 평가)로 정한다. 체결일 종가는 쓰지 않는다.
  - 목표 수량 = floor(비중 × 가치 × (1 − 현금 버퍼 1%) / 신호일 종가).
  - 목표에 없는 보유 종목은 **금액과 무관하게 전량 매도**한다(해석: $200 생략은 '조정'에만 적용).
  - 신규 매수 금액(0주 포함)이나 조정 금액이 $200 미만이면 생략하고 건수·금액을 센다.
  - 못 산 금액 = Σ max(0, 목표 금액 − 실행 후 보유 금액)이다.
  - 신호일 종가 기준 매수 총액이 (현금 + 매도 대금)을 넘으면 매수를 비례 축소한다(`scaled`).
- **체결(계획서 9장):** 체결일(신호일 다음 거래일) 개장 30분 뒤 예약 이벤트에서 매도 먼저, 그다음 매수를 `market_on_close_order`로 낸다. 매도는 그 시점 보유 수량보다 많이 내지 않는다(그 사이 상장폐지·청산 대비). 신호일 월말 종가로는 체결하지 않는다.
- **가격 기준:** 매매 종목은 원주가(`DataNormalizationMode.RAW`)로 구독한다. 수량 계산 가격과 체결가가 같은 기준이고, 배당은 현금으로 들어온다. 모멘텀·σ̂는 따로 받은 조정 가격으로 계산한다.
- **무차입(계획서 4장):** 목표 비중 합은 99% 이하이고, 매 거래일 전날 체결 결과로 현금 음수(`neg`, 첫 발생은 `[WARN]`)와 최대 노출(`max_expo`)을 기록한다.
  - LEAN 주문 검증 한도는 margin 기본 2배(`BUYING_POWER_LEVERAGE`)로 둔다. 같은 MOC에서 매도 대금이 체결되기 전 매수 주문이 매수력 부족으로 거절되지 않게 하기 위해서다. 실제 노출을 늘리는 용도가 아니다([L]).
- **비용:** LEAN Interactive Brokers 브로커·수수료 모형(`BrokerageName.INTERACTIVE_BROKERS_BROKERAGE`, `AccountType.MARGIN`)을 쓴다.
  - LEAN IB 수수료 모형은 IB **Fixed** 요율(미국 주식 주당 $0.005, 주문당 최소 $1, 거래 금액 대비 상한)로 알고 있다. Tiered는 모형에 없다. 상한 비율(0.5% 또는 1%)과 정확한 계산은 **확인 필요**다([L]). `[FILL]` fee와 `[PYEAR]` 수수료로 확인한다.
  - 스프레드·슬리피지와 저/기본/고 시나리오는 4단계에서 넣는다.
- **Stage 0 항목(기록만):** 실계좌를 현금 계좌로 할지(현금 계좌의 결제 기간 제한 T+2/T+1 등)는 Stage 0에서 정한다. 이번 백테스트는 margin 계좌 모형이고 레버리지는 쓰지 않는다.
- **구현하지 않은 계획서 제약:** 4장 '주문 ≤ 20일 평균 거래대금의 1%'는 이번 단계에 넣지 않았다. $20,000 계좌의 주문(수백 달러)은 유니버스 종목의 거래대금에 비해 매우 작다. 4단계 비용 모형과 함께 넣을지 결정이 필요하다.
- **속도 단축(결과 동일):**
  - `QUICK_TEST = True`면 실행 구간이 2001-01-01~2004-12-31이다(개발 구간 검사는 그대로). 2001~2002는 스냅샷·모멘텀 준비 구간이다. 1998 시작 실행과의 비교는 "기록" 참고.
  - 선택 함수는 '현재 보유 + 이번 매수 예정' 종목만 반환해 LEAN 구독을 줄인다. 유니버스·z 대상은 코드 안의 집합이다. `SUBSCRIBE_ALL_MEMBERS = True`면 2단계처럼 유니버스 전체를 구독한다(비교용).
  - 조정 일봉은 모멘텀과 σ̂에 함께 쓰도록 월 1회 묶음으로 요청한다. 역변동성이면 신호일 400일 전부터, 끝은 신호일 봉까지다.
  - 가짜 QC 시험에서 구독 축소 전후의 유니버스·z·계획·체결·로그가 같았다. 유니버스·z는 2단계와 같았다.
- **정수 주 영향:** $20,000에 N=60이면 한 자리가 약 $330이다. 주가가 높은 종목은 1주 단위 내림으로 못 산 금액이 크고, 주가가 $330보다 높으면 신규 매수가 생략된다. `[REBAL]` `unbought`·`skip`, `[PYEAR]` `cash`로 크기를 본다.
- **[L] 확인 필요(LEAN API·동작):**
  - MOC 제출 시각 제한: LEAN은 MOC를 장 마감 일정 시간(기본 15.5분으로 알고 있음) 전까지만 받는 것으로 안다. 개장 30분 뒤 제출이므로 조기 폐장일에도 여유가 있다. 거절되면 `[PYEAR]` `rej`로 나온다.
  - 일봉 해상도의 MOC 체결: 일봉이 16:00에 끝나면(`daily_precise_end_time` 기본값) 그 봉의 종가로 체결되는 것으로 안다. `[FILL]`의 fill = close(ok)와 filled 시각(체결일 16:00)으로 확인한다.
  - 새로 구독한 종목의 가격: `FuncSecuritySeeder(self.get_last_known_prices)`로 시드한다. 시드가 안 되면 가격 0으로 주문이 거절될 수 있다(`rej`).
  - 주문 검증 한도: 같은 시각 대기 중인 매도 대금을 LEAN 매수력 검증이 반영하는지 확인하지 못해 한도를 2배로 두었다. `rej`가 0이고 `neg`가 0이면 문제가 없다.
  - 유니버스에서 빠진 보유 종목: 선택 함수가 보유 종목을 항상 반환하므로 보유 중에 구독이 끊기지 않는다. 보유 중인 종목은 LEAN이 유니버스에서 제거하지 않는 것으로 안다.
  - 상장폐지: LEAN이 상장폐지일에 보유분을 자동 청산하는 것으로 알고 있다. `on_data`의 `data.delistings`(`DelistingType.DELISTED`)로 보유 종목 이벤트를 센다(`delist`).
  - RAW 구독에서 배당 현금 입금·분할 수량 조정은 LEAN이 처리하는 것으로 안다.
  - `get_parameter(이름, 기본값)`·`set_runtime_statistic`·`schedule.on(date_rules.every_day, time_rules.after_market_open)` 사용법.

## 기록 (실행 관측과 결정)

- **1998~2002년 적격 종목 부족(2026-09-26 실행):** Morningstar 커버리지 때문에 적격 종목이 900개 미만인 달이 있다. 그 달은 적격 종목 전체가 유니버스가 된다(`[YEAR]`의 `short`, `[SUMMARY]`의 `short_months`). 계획서 6장 규칙(진입 900 / 유지 1,100)은 바꾸지 않고 기록만 한다.
  - 결정(2026-09-26): `[START]`은 데이터 존재 점검용이므로 통과 조건에서 '적격 종목 ≥ 900'을 뺐다(`bar_at_sig`·`price_match`·`filing`만 본다). 적격이 900개 미만이면 `[START]` 줄 끝에 `eligible<900 (NOTES 기록 참고)`만 표시하고 보류하지 않는다.
- **Morningstar `market_cap`은 회사 전체 값(2026-09-26 실행):** `[DIAG]` share_class 줄에서 BRKA·BRKB가 모두 `mcap=62.1B`였다. 주식 종류별 시총이 아니라 같은 회사의 전체 시총이 각 종류에 붙어 있다는 뜻이다. 그래서 대표 주식만 고르고 종류별 시총은 합산하지 않는다(합산하면 이중 계산).
- **점수 산출 기간은 1999-01 신호일부터(2단계):** 가격 데이터가 1998-01-02부터 시작하고, 12-1 모멘텀은 12개월 관측이 필요하기 때문이다([K]). 1998년 신호일은 유니버스만 만들고 점수는 없다(`[FYEAR 1998]` `cov_avg=0.000`). `[FACTOR]` 월별 상세는 점수가 처음 나온(scored > 0) 두 신호일에 남긴다(`config.FACTOR_DETAIL_MONTHS`).
- **[SPOT] 실측 대조(2단계 첫 QC 실행):** IBM·MSFT·XOM의 시총, TTM 매출, TTM 순이익, 총자산이 실제 재무제표와 일치했다. Morningstar 금액 단위 문제(천 달러 등)는 없다. [J]의 필드 이름(`total_revenue`·`net_income`·`total_assets` 등)과 금액 단위가 이 대조로 확인됐다.
- **합병 직후 비율의 일시 왜곡(PIT 규칙상 정상):** 합병 직후(예: 1999-12 XOM, 엑슨-모빌 합병 1999-11-30)에는 시총은 합병 후 주식 수로 계산되고, 재무는 아직 합병 전 공시(사용 가능한 마지막 공시)라 가치·퀄리티 비율이 일시적으로 왜곡될 수 있다. 공시 다음 거래일 규칙을 지킨 결과이며, 합병 후 첫 공시가 사용 가능해지는 달부터 정상화된다. 규칙은 바꾸지 않는다.
- **history() 반복 호출 경고(의도된 동작):** 모멘텀은 매월 유니버스 종목 전체의 배당·분할 조정 일봉을 history()로 다시 요청하고, QC는 이를 반복 호출 경고로 표시한다. 조정 가격은 요청 시점을 기준으로 다시 계산되므로(그 사이 배당·분할이 있으면 과거 조정가가 바뀜), 예전에 받은 조정가를 저장해 이어 붙이면 기준이 섞인다. 그래서 매월 새로 요청하는 것이 의도된 동작이다.
- **평가 시작 2003-01 신호일(사용자 결정, 3단계, 수익률과 무관):**
  - 이유: 1998~2002는 Morningstar 커버리지 때문에 적격 종목이 900개 미만이라 유니버스가 '적격 전체'가 되어 소형·저유동 종목이 섞인다. 3단계 첫 QUICK_TEST 실행에서 QC 추정 capacity는 $23,000이었고, 최저 capacity 종목은 ANK였다. 계획서 6장의 대형주 유니버스 전제가 성립하지 않는다.
  - 처리: 2003-01 이전 신호일은 유니버스·z만 계산하고 주문하지 않는다. 알고리즘 시작일은 1998-01-01 그대로다(검증된 유니버스 경로 유지). `[CONFIG]` 3단계 줄에 `portfolio_start=2003-01`과 이유를 찍는다.
  - 1999~2002 결과(유니버스·z)는 '데이터 한계 구간'으로만 참고한다.
- **QUICK_TEST 시작일 2001-01-01 검토(가짜 QC 시험):**
  - 2002년까지 적격 < 900이고 매달 시총 순위가 바뀌는 가짜 데이터에서, 2001 시작과 1998 시작 실행을 비교했다.
  - 결과: 유니버스는 처음부터 같았고, z는 2001-11 신호일부터 같았다(초기에는 분기 스냅샷이 부족해 TTM·평균 총자산이 다름). 2003-01 신호일의 유니버스·z, 이후 모든 달, 주문이 모두 같았다. `[REBAL]` #1 지문도 같았다. 그래서 시작일을 2001-01-01로 유지한다.
  - 이유: 1단계 결과상 2003년 전에는 유니버스가 900 미만(=적격 전체)이라 완충 경로가 시작일과 무관하다. 재무 스냅샷은 4개 분기와 1년 전 총자산에 약 12~15개월이면 충분하다.
  - 대조(처음부터 적격 ≥ 900)에서도 가짜 데이터에서는 2003-01 차이가 0이었다. 다만 실제 데이터 보장은 아니다.
  - QC에서 확인: 빠른 실행과 전체 실행의 `[REBAL] #1 … uni=… zt=…`가 같아야 한다.
- **데이터 커버리지 점검 모드(`COVERAGE_CHECK`, 전략 로직과 무관):**
  - 목적: 적격 종목이 2003년 약 1,100개·2015년 약 1,400개이고, 900위 시총(cut900)이 2003년 $0.19B·2015년 $0.90B로 작다. QC Morningstar 데이터에서 과거 종목(특히 대형주)이 빠졌는지, 빠졌다면 어떤 종목인지 확인하려는 것이다.
  - 사용법: `config.COVERAGE_CHECK = True`로 바꿔 실행한다. 실행 구간은 2002-12-01~2015-01-31이고 QUICK_TEST보다 우선한다. 끝나면 False로 되돌린다.
  - 동작: 팩터·주문·스냅샷·첫 신호일 확인을 하지 않고, 점검일(2003-01, 2007-06, 2011-06, 2014-12의 신호일)에만 1단계 선별을 돌린다. 나머지 달은 아무것도 하지 않아 빠르다. LEAN 구독은 없다. `[CONFIG]`은 1·2단계 줄과 `mode=coverage_check` 줄을 남기고, 끝에 `[COV] done`을 남긴다(`[SUMMARY]`·`[PERF]` 없음).
  - `[COV 신호일]` 한 점검일에 4줄:
    1. `total`(선택 함수 입력 수), `fund`(재무 있음), `eligible`(1단계 적격), `cut900`, 재무 없는 종목 중 가격 ≥ $5인 수와 일 거래대금 ≥ $5M·$20M·$100M 수.
    2. 재무 없는 종목의 거래대금 상위 20개(`티커:가격:거래대금 백만 달러`).
    3~4. `checka`·`checkb`: 알려진 대형주 30개(GOOG는 2004-08 이후 점검일만). `#순위` = 적격이며 적격 종목 중 시총 순위(완충과 무관), 1단계 탈락 사유 코드(`no_fund`·`type`·`adr`·`exchange`·`share_class`·`price`·`country`·`sector_na`·`sector_Fin`·`reit`·`listing` 등), `missing` = 선택 함수 입력에 없음.
  - 런타임 통계 `cov_YYYYMM` = `tot fund elig nf20M(재무 없음·$20M 이상) ok(점검 목록 중 적격)/점검 수 miss(입력에 없음)`.
  - 해석 주의:
    - 재무 없는 종목에는 ETF가 섞여 있어(ETF는 재무가 없음) 상위 20개는 대부분 ETF일 수 있다. 대형주 누락은 3~4줄의 점검 목록으로 본다.
    - 거래대금은 신호일 하루 값이다.
    - `share_class` 탈락은 같은 회사의 다른 주식 종류가 대표로 뽑힌 경우다(예: GOOG 대신 GOOGL).
  - **[M] 확인 필요:** `Fundamental.dollar_volume` 속성이 있는지. 없으면 가격 × `volume`으로 대신 계산하고, 둘 다 없으면 0으로 센다.
